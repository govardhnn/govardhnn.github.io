Advanced Superscalar Architectures

A superscalar processor sustains more than one instruction per cycle: it fetches, decodes, renames, issues, executes, and commits several at once. Where Out of Order Execution and Register Renaming supplies the algorithms, this note is about the machine: what issue width does to every structure, and why width stopped at ~4-8 even as transistor budgets exploded.

The Iron Law view: pipelining attacks cycle time, superscalar attacks CPI, pushing IPC above 1 toward the machine width ww. Achieved IPC is limited by the program’s instruction-level parallelism (ILP), not the datapath.

In-Order Superscalar First

The original Pentium (1993) issued 2 instructions per cycle in order, with pairing rules (both simple, no dependence, one memory op) checked at decode; unpaired instructions issued alone. Cheap, but in-order issue means one stalled instruction blocks its pair: real IPC ~1.1-1.4. In-order superscalar survives where energy dominates (little cores, many embedded designs); everything else went out of order.

Frontend at Width

Fetch must deliver ww useful instructions per cycle, every cycle:

  • A fetch group is one I-cache access; a taken branch mid-group wastes the rest of the line, and a target entering mid-line wastes its start. Fetch alignment plus ~1 taken branch per 5-8 instructions caps naive fetch bandwidth below ww.
  • Fixes: fetch across line boundaries (two banks), predict multiple branches per cycle (Branch Prediction BTB indexed by fetch group), and a decoupled fetch queue so the frontend runs ahead.
  • The trace cache (Pentium 4) stored instructions in predicted dynamic order to fix this; its modern descendant, the µop cache, caches decoded µops and doubles as a decode-power saver.

Decode at width is where ISA encoding matters (RISC-V ISA comparison table): fixed 32-bit instructions decode in parallel trivially; x86’s 1-15 byte instructions need speculative length decoding, so x86 cores split decoders into complex+simple sets and lean on the µop cache. CISC instructions crack into µops; some RISC-like pairs fuse (compare+branch) into one µop.

Backend at Width

Everything scales worse than linearly in ww:

  • Register file ports: 2w2w read + ww write ports; port count grows area roughly quadratically and hurts access time, so wide cores bank or replicate the PRF (Sequential Circuits register file, multiplied).
  • Bypass network: every FU output to every FU input is O(w2)O(w^2) wires and muxes, and wire delay dominates below 100 nm; wide machines stage bypasses (same-cycle only within a cluster).
  • Issue queue wakeup-select: each broadcast tag must CAM against every waiting operand, then select must arbitrate among all ready instructions, and the loop must close in one cycle or dependent instructions cannot issue back-to-back:

Reading Operands: Before or After Issue

A width-independent design fork hides inside the issue queue: when is the register file read?

  • Read before issue (Tomasulo’s heritage): read available operands at dispatch and store the values in the issue queue; missing ones arrive over the bypass. Fewer register-file ports, but the queue becomes a second register file: values are written into it, read out of it, and copied again, all of it energy. The natural partner of ROB/rename-buffer renaming, where a value may otherwise have to be chased from buffer to architectural file mid-flight.
  • Read after issue: the queue holds only operand identifiers; the physical file is read after select. More ports, but each value is read once from one place. The natural partner of the merged register file, and the modern default.

Bypass and the Clustering Ladder

Deep pipelines make the bypass worse than O(w2)O(w^2) suggests: a result must be forwardable from several pipeline stages (ALU output, result drive, writeback) to catch consumers issued 1, 2, or 3 cycles behind, so each of the w2w^2 paths is really several. Two standing simplifications: the FP/SIMD units get a bypass network of their own (integer results almost never feed FP directly), and the memory unit hangs off both.

The bypass you can refuse

IBM’s POWER4 and POWER5 shipped with no bypass network at all: dependent integer ops pay a 1-cycle bubble, dependent FP ops six. The designers bought frequency and simplicity, and let out-of-order execution fill the bubbles with independent work, a reminder that every “mandatory” structure is actually a trade.

When the bypass or the register file does threaten the clock, designers climb the clustering ladder, each rung cutting more wire at more IPC cost:

  1. Cluster the bypass only: full forwarding inside a cluster, none across; a cross-cluster value takes the long way through the register file.
  2. Replicate the register file (Alpha 21264): each cluster owns a complete copy, kept coherent by broadcasting every result; a value born in cluster 0 is usable in cluster 1 one cycle later. Each copy needs only half the read ports, which is what let the 21264 hit its clock. The issue queue stays unified, with one arbiter per cluster.
  3. Distribute the issue queue and register file: no copies at all: each cluster holds half the registers and its own queue, instructions are steered to a cluster at rename, and cross-cluster values move by explicit copy operations. Cheapest wires, hardest scheduling problem: steering must keep dependent instructions together while keeping the load balanced.

Commit at Width

Commit is the pipeline’s other in-order regime: a ww-wide machine scans a whole ROB row and retires it greedily. The interesting design is recovery, because its two triggers have opposite frequencies. Branch mispredictions are common, so they get the fast path: a rename-map checkpoint per branch, restored in one cycle. Exceptions are rare, so they may take the slow path: wait until the faulting instruction reaches the head, then unwind. BOOM implements both ends configurably: rollback walking the ROB one row per cycle (R10000 style), or an extra committed map table that resets rename state in a single cycle. Its issue queues are equally concrete: separate memory/integer/FP queues (16 entries each at 1/2/1 issue ports in the base configuration), age-ordered by default because the cheaper position-based policy can starve old branches.

Limits of ILP

Classic limit studies (Wall 1991; H&P) give a perfect-machine ILP of dozens to hundreds, but every realism cut is brutal: finite window, real branch prediction, finite registers, and real memory latency bring sustainable IPC on integer code to ~2-4. Dependence chains are the floor: a pointer chase executes at 1 instruction per load latency no matter the width.

That, plus the O(w2)O(w^2) structures and the ~1.5-2x energy per instruction of aggressive speculation, is why width plateaued and the transistor budget went to caches and cores instead (History of Computing power wall). Recent cores widened again (Apple M-series ~8-10 wide) by spending enormous µop caches, predictors, and windows to keep a low clock and low voltage: width as an energy play, the inverse of the GHz race.

Simultaneous Multithreading

A single thread cannot fill a wide machine: vertical waste (whole cycles idle, e.g. cache miss) and horizontal waste (some of the ww slots idle). Multithreading fills waste with other threads’ work:

  • Coarse-grain: switch threads on a long stall; fills only vertical waste, costs a switch penalty.
  • Fine-grain: rotate threads every cycle (barrel processors, GPU warps); fills vertical waste, kills single-thread latency.
  • SMT: issue from multiple threads in the same cycle; the only scheme that fills horizontal waste. In an OOO core it is remarkably cheap: duplicate the PC, rename map, and architectural state; share the IQ, PRF, FUs, and caches; tag every µop with a thread ID. Intel’s Hyper-Threading is 2-way SMT for ~5% area and typically 15-30% throughput.

Costs: threads compete for caches and predictor state (a cache-thrashing sibling can slow the machine), fairness needs explicit fetch policies (ICOUNT: fetch for the thread with fewest µops in flight), and shared-resource leakage created a family of SMT side channels; security-sensitive deployments disable it.

Evolution Case Study

Core Year Width Depth Window Note
Pentium 1993 2 in-order 5 - pairing rules
Pentium Pro 1995 3 ~12 40 µops + OOO + PRF-in-ROB
Pentium 4 2000 3 20-31 126 trace cache, GHz race, power wall
Core 2 2006 4 14 96 retreat to efficiency
Skylake 2015 4-5 ~14 224 µop cache, SMT
Apple M1 2020 ~8 ~13 ~630 width at low clock

The P4 → Core 2 reversal is the syllabus in one row: deeper+faster lost to wider+cooler once power became the constraint.

Reliability

Shrinking transistors made a new failure class architectural: soft errors, bit flips from cosmic-ray neutrons and alpha particles that corrupt state without damaging hardware (rate measured in FIT, failures per 10910^9 hours; it grows with transistor count, so big machines see them daily). The defenses are layered by cost:

  • Parity on structures whose contents can be refetched: an I-cache or clean D-cache line that fails parity is simply invalidated and re-read; detection alone suffices.
  • ECC (SECDED: single-error correct, double-error detect, 8 check bits per 64 data bits) on anything holding the only copy: dirty cache lines, register files, DRAM. Server DRAM adds chipkill to survive a whole failed chip, and scrubbing walks memory correcting single-bit errors before a second one compounds them.
  • Redundant execution where the pipeline itself must be trusted: lockstep cores compare retirement results cycle by cycle (automotive/avionics), and TMR (triple modular redundancy) votes three copies to mask an error outright, the same majority trick at the system level that spacecraft use.

Speculation machinery gives OOO cores a cheap trick: an error detected before commit (a parity-failing µop result, a mis-voted structure) can often be handled by the existing squash-and-replay path, turning a potential silent data corruption into a transparent retry.
