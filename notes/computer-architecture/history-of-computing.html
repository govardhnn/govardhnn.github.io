History of Computing

Computer architecture is the science of building computers that are fast, cheap, and correct under a given technology. Its history is a loop: a technology shift enables a new machine organization, the organization becomes an abstraction, and the abstraction outlives the technology that created it. The two abstractions that survived everything are the stored-program computer and the instruction set architecture (ISA).

Mechanical Prehistory

Charles Babbage’s Difference Engine (1822) mechanized polynomial evaluation with fixed-function gears. His Analytical Engine (1837, never completed) was the first general-purpose design: a mill (ALU), a store (memory), punched-card program input, and conditional branching. Ada Lovelace’s notes on it contain the first published program and the insight that a machine manipulating symbols could compute more than numbers.

Herman Hollerith’s punched-card tabulators (1890 US census) made data processing a business, and his company became part of IBM. Cards separated program from machine long before electronics did.

The Stored-Program Computer

Electromechanical and electronic machines of the early 1940s (Zuse Z3 1941, Harvard Mark I 1944, Colossus 1943, ENIAC 1945) were programmed externally: plugboards, switches, or paper tape. Reprogramming ENIAC took days of rewiring even though it computed in microseconds.

The fix, articulated in von Neumann’s First Draft of a Report on the EDVAC (1945), is the stored-program concept: instructions are data, held in the same addressable memory, so the machine can load, and even generate, its own programs. EDSAC (Cambridge, 1949) was the first practical stored-program computer.

Two memory organizations follow:

von Neumann Harvard
Memory one, shared program + data separate instruction and data memories
Bottleneck single port (the von Neumann bottleneck) dual bandwidth
Flexibility code as data (compilers, loaders, JIT) code fixed or loaded specially

Every modern core is a modified Harvard machine: a single memory space (von Neumann contract for software) accessed through split instruction and data caches (Harvard structure for bandwidth). Caches are covered in Caches and Virtual Memory.

The 1950s: Making Programs Cheaper

Commercial machines (IBM 650, 704) added features that moved work from programmer to hardware:

  • Index registers (Manchester Mark I): address modification by hardware instead of self-modifying code, enabling clean loops over arrays.
  • Subroutine linkage conventions, the ancestor of calling conventions in RISC-V ISA.
  • Floating point hardware (IBM 704, 1954), the ancestor of Floating Point Architecture.
  • Magnetic core memory: random access, non-volatile, dominant until DRAM (1970s).
  • The first high-level language (Fortran, 1957) proved compilers could rival hand assembly, a result that later powered the RISC argument.

The 1960s: ISA vs Implementation

The IBM System/360 (1964) introduced the idea that defines architecture as a discipline: one instruction set architecture, many implementations. The 360 family spanned a 50x price range, from a slow byte-serial machine to a fast parallel one, all binary compatible. The ISA is the contract (registers, instruction encodings, memory model); the microarchitecture is any implementation honoring it. Software investment survives hardware generations; the S/360 lineage still runs today as z/Architecture.

Stack, Accumulator, and Register Machines

Where operands live is the first ISA design decision, and the industry tried every answer. Compare C = A + B:

Style Machines Code Operands
Stack Burroughs B5000, JVM bytecode push A; push B; add; pop C implicit, top of stack
Accumulator EDSAC, 6502 load A; add B; store C one implicit register
Register-memory S/360, x86, 68000 load r1,A; add r1,B; store r1,C registers + memory operands
Load-store (register-register) CDC 6600, all RISCs ld r1,A; ld r2,B; add r3,r1,r2; st r3,C registers only; loads/stores move data

Stack code is dense and trivially compilable but serializes everything through the stack top and hides operand reuse; accumulator machines make the single register a structural hazard; register-memory ISAs grew rich addressing modes (the VAX had 13, including memory-indirect) that made instruction latency wildly variable. General-purpose registers won because registers are faster than memory, compilers allocate them well (graph coloring, 1981), and explicit operands expose the parallelism that pipelines and OOO cores need. The load-store subset won within GPR designs for the same reason: memory access isolated into two instruction types is easy to pipeline. Stack machines survive as virtual ISAs (JVM, WebAssembly), where density beats parallelism because a JIT recompiles to registers anyway.

Microprogramming

The key technique enabling one-ISA-many-implementations was microprogramming (Wilkes, 1951): the control unit is itself a tiny stored-program machine, executing microinstructions from a fast control ROM to sequence each ISA instruction’s register transfers. Cheap 360 models interpreted the same ISA with narrow datapaths and more microcode steps; expensive ones used wider datapaths and fewer. Horizontal microcode encodes each datapath control signal as its own bit (wide words, one step per cycle, minimal decoding); vertical microcode encodes compactly and decodes each microword (narrower ROM, more steps), the same density-vs-speed trade as CISC vs RISC one level down. Because a new instruction was just more ROM, microcode made rich instructions nearly free to define, which led directly to CISC ISAs like the DEC VAX (1977), where a single instruction could evaluate a polynomial.

Microcode faded as main memory caught up with control-store speed (interpreting from ROM lost its edge over executing simple instructions from cache) and hardwired control enabled pipelining. It survives in two places: x86 decoders translate common instructions directly into micro-ops but fall back to a microcode sequencer for the rare complex ones (string moves, transcendentals, system entry), and field-updatable microcode is now the patch channel for CPU bugs and security mitigations (Spectre-era updates shipped as microcode).

In the same years the CDC 6600 (Cray, 1964) took the opposite path: a lean load-store instruction set, ten parallel functional units, and a scoreboard issuing instructions out of order, making it roughly 10x faster than anything else. It was RISC and out-of-order execution before either had a name.

The Microprocessor and the RISC Revolution

The Intel 4004 (1971) put a CPU on one chip; the 8080/8086 line and Motorola 68000 rode Moore’s law (transistor count doubling roughly every two years, observed 1965) into general-purpose computing.

By 1980, measurements (IBM 801, Patterson’s Berkeley RISC, Hennessy’s Stanford MIPS) showed compilers used only a small, simple subset of CISC instructions, while the complex ones made every instruction slower (longer decode, microcode indirection). The RISC argument, stated with the Iron Law below: give up instructions/program to win cycles/instruction and cycle time.

  • Fixed-length, easy-to-decode encodings
  • Load-store architecture: only loads/stores touch memory
  • Large general-purpose register file, compiler does the scheduling
  • Hardwired control instead of microcode, enabling the pipelines in Simple Instruction Pipeline

Commercial RISCs (MIPS, SPARC, POWER, ARM) followed. x86 survived by translating CISC instructions into RISC-like micro-ops internally (Pentium Pro, 1995), so every modern x86 is a RISC engine behind a CISC decoder. The open RISC-V ISA (2010) is the current distillation of these lessons.

Scaling Eras and Walls

Dennard scaling (1974): shrinking a transistor by kk lets voltage and delay shrink by kk too, so power density stays constant, and frequency rises for free. Together with Moore’s law this drove single-core performance ~50%/year into the 2000s, absorbed by deeper pipelines, Branch Prediction, superscalar issue, and out-of-order execution.

Three walls ended it around 2005:

Wall Cause Consequence
Power Dennard scaling broke (leakage, VddV_{dd} stopped dropping) frequency froze near 3-5 GHz
ILP diminishing returns on wider/deeper speculation issue width stalled at ~4-8
Memory DRAM latency improved far slower than core speed deep cache hierarchies rule performance

The industry pivot: spend transistors on multicore (bringing Multicore Cache Coherence and the Memory Model to the foreground), then on dark silicon and domain-specific accelerators (GPUs, TPUs), trading generality for energy efficiency. Power techniques live in Synthesis, Timing and Power.

Performance Fundamentals

The Iron Law decomposes execution time and assigns each factor an owner:

timeprogram=instructionsprogram⏟algorithm, compiler, ISA×cyclesinstruction⏟microarchitecture×timecycle⏟circuits, technology\frac{\text{time}}{\text{program}} = \underbrace{\frac{\text{instructions}}{\text{program}}}_{\text{algorithm, compiler, ISA}} \times \underbrace{\frac{\text{cycles}}{\text{instruction}}}_{\text{microarchitecture}} \times \underbrace{\frac{\text{time}}{\text{cycle}}}_{\text{circuits, technology}}

CPI (cycles per instruction) and its reciprocal IPC are the microarchitect’s score. Every technique in these notes is an attack on one factor that must not give back more in the others: RISC raises instructions/program to cut CPI and cycle time; pipelining cuts cycle time at a small CPI cost; superscalar cuts CPI below 1.

Amdahl’s law bounds any speedup by the fraction of time it touches. Accelerating a fraction ff of execution by ss:

speedup=1(1−f)+f/s\text{speedup} = \frac{1}{(1-f) + f/s}

If 60% of runtime is parallelizable and gets 16 cores, speedup is 1/(0.4+0.6/16)=2.291/(0.4 + 0.6/16) = 2.29, not 16. The corollary: make the common case fast, and the uncommon case correct.

Benchmarks. MIPS and peak FLOPS mislead (they ignore instruction count differences and achievable utilization); wall-clock time on representative suites (SPEC CPU for cores, TPC for transactions) is the standard. Throughput (jobs/second) and latency (seconds/job) are different targets: pipelining boosts throughput while slightly hurting single-instruction latency.
