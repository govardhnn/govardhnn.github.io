Branch Prediction

Roughly one instruction in five is a branch, and the fetch stage of the Simple Instruction Pipeline must produce a next PC every cycle, long before the branch resolves. A branch predictor guesses the outcome so fetch never waits; a wrong guess flushes speculative work. Prediction is the enabling technology for deep pipelines and for all speculation in Out of Order Execution and Register Renaming.

The cost of control flow in CPI terms:

CPIbranch=fbranch×pmispredict×penaltyCPI_{branch} = f_{branch} \times p_{mispredict} \times \text{penalty}

At f=0.2f=0.2, a 20-cycle penalty (typical modern pipeline depth to resolution), and 95% accuracy: 0.2×0.05×20=0.20.2 \times 0.05 \times 20 = 0.2 extra CPI, a ~20% slowdown from just 5% of branches. Accuracy must scale with depth and width, which is why predictors grew from 2-bit counters to TAGE.

What Must Be Predicted

Fetch needs three answers about the bytes it just fetched, before decoding them:

  1. Is any of this a branch? Answered by the BTB hit (or predecode bits in the I-cache).
  2. Taken or not? The direction predictor.
  3. Where to? The target: BTB for branches/jumps, return address stack for returns, indirect predictor for computed jumps.

Static Prediction

  • Always not-taken: trivial (keep fetching sequentially); ~30-40% accurate on typical code since loops branch backward-taken.
  • BTFN (backward taken, forward not-taken): backward branches are loop bottoms, so predict them taken; ~65% accurate with zero state.
  • Compiler hints / profiling: ISA bits suggesting a direction from profile runs; static limits are ~75-80% because data-dependent branches cannot be predicted at compile time.

Dynamic Direction Prediction

1-bit: remember the last outcome per branch. A loop branch mispredicts twice per loop execution (once at entry, once at exit): a 100-iteration loop gets 98%, a 4-iteration inner loop only 50%.

2-bit saturating counter: add hysteresis so a single anomaly does not flip the prediction. Increment on taken, decrement on not-taken, saturate at both ends; predict from the high bit:

The loop-exit misprediction no longer flips the state, so the next entry predicts correctly: one misprediction per loop execution.

Branch history table (BHT): an array of 2-bit counters indexed by low PC bits (e.g. 4K entries). Untagged, so two branches mapping to the same entry interfere (aliasing); usually tolerated because counters are cheap.

Correlating Predictors

Many branches correlate with other branches or with their own history pattern:

if (x < 1) ...      // b1
if (x > 1) ...      // b2: never taken when b1 was taken

A global history register (GHR) shifts in the outcome of every branch (last hh outcomes). Two-level predictors index a pattern history table (PHT) of 2-bit counters using history and PC together.

gshare is the classic hash: index = PC XOR GHR, spreading (branch, history) pairs across the PHT:

Local history keeps a per-branch history register instead (captures patterns like taken-taken-not repeating); tournament predictors (Alpha 21264) run global and local side by side with a chooser table of 2-bit counters learning which to trust per branch.

Modern predictors in one paragraph: TAGE uses multiple tagged tables indexed with geometrically increasing history lengths (5, 10, 20, … hundreds of bits) and predicts from the longest history that hits, backed by a base bimodal table; perceptron predictors compute a weighted sum of history bits. Both reach ~99%+ on SPEC-like codes and are combined in shipping cores.

Target Prediction

Branch target buffer (BTB): a small tagged cache, indexed by fetch PC, holding the predicted target and branch type. A BTB hit simultaneously answers “this is a branch” and “fetch from here next”, redirecting fetch with zero bubbles:

Return address stack (RAS): returns jump wherever the caller was, so a BTB entry is useless. A small hardware stack (8-32 entries) pushes PC+4 on every call and pops on every return; near-perfect until call depth overflows it. Speculative pushes/pops must be repaired on misprediction.

Indirect branches (virtual calls, switch tables, interpreter dispatch) have many targets per site; predicted with history-indexed target tables (ITTAGE), historically the worst-behaved class.

Living in the Pipeline

  • Predict in IF: BTB/direction lookup happens in parallel with the I-cache access, producing the next fetch PC.
  • Verify when the branch executes (EX, or at commit): compare actual outcome/target with prediction.
  • Recover on mismatch: squash all younger instructions, restore fetch to the correct path, and repair predictor state (GHR, RAS). In-order pipes flush stages; out-of-order machines restore a checkpoint, the same machinery as Exceptions recovery. A clean implementation tags every instruction with an epoch; instructions from stale epochs are discarded wherever they are.
  • Update the tables at resolve/commit with the true outcome.

Measuring: accuracy alone misleads across programs with different branch densities; MPKI (mispredictions per kilo-instruction) composes directly with penalty into CPI. And why 95% is not enough: at depth 20 and width 4, one misprediction wastes up to 80 issue slots, so the gap between 95% and 99% is roughly a 4x reduction in speculation waste, which is also energy (Synthesis, Timing and Power).

Security aside: predictor state is shared microarchitectural state trained by one context and consumed by another; Spectre showed mistrained speculation leaks data through cache side channels, and modern cores add predictor isolation/flush controls on privilege switches.
