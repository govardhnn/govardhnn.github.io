Branch Prediction

Branch prediction supplies a likely next PC before control flow resolves. Correct predictions keep fetch busy; wrong predictions require recovery. The benefit depends on branch frequency, accuracy, and penalty.

The cost of control flow in CPI terms:

CPIbranch=fbranch×pmispredict×penaltyCPI_{branch} = f_{branch} \times p_{mispredict} \times \text{penalty}

At f=0.2f=0.2, a 20-cycle assumed recovery penalty, and 95% accuracy: 0.2×0.05×20=0.20.2 \times 0.05 \times 20 = 0.2 extra CPI, a 20% slowdown if baseline CPI is 1 and penalties do not overlap. Accuracy must scale with depth and width, which is why predictors grew from 2-bit counters to TAGE.

What Must Be Predicted

Fetch needs three answers about the bytes it just fetched, before decoding them:

  1. Is any of this a branch? Answered by the BTB hit (or predecode bits in the I-cache).
  2. Taken or not? The direction predictor.
  3. Where to? The target: BTB for branches/jumps, return address stack for returns, indirect predictor for computed jumps.

Static Prediction

  • Always not-taken: continue sequential fetch.
  • BTFNT: predict backward branches taken and forward branches not taken.
  • Compiler hints/profiling: use static information; accuracy depends on the workload.

Small cores may omit dynamic prediction when its area and power outweigh the avoided stalls.

Dynamic Direction Prediction

1-bit: remember the last outcome per branch. After warm-up, a repeated loop with taken iterations and one not-taken exit can mispredict twice per invocation (once at entry, once at exit): a 100-iteration loop gets 98%, a 4-iteration inner loop only 50%.

2-bit saturating counter: add hysteresis so a single anomaly does not flip the prediction. Increment on taken, decrement on not-taken, saturate at both ends; predict from the high bit:

For a loop with several taken iterations, a strongly taken counter survives one not-taken exit, so the next entry predicts correctly. Aliasing and very short loops can change this behavior.

Branch history table (BHT): an array of 2-bit counters indexed by low PC bits (e.g. 4K entries). Untagged, so two branches mapping to the same entry interfere (aliasing); usually tolerated because counters are cheap.

Correlating Predictors

Many branches correlate with other branches or with their own history pattern:

if (x < 1) ...      // b1
if (x > 1) ...      // b2: never taken when b1 was taken

A global history register (GHR) shifts in the outcome of every branch (last hh outcomes). Two-level predictors index a pattern history table (PHT) of 2-bit counters using history and PC together.

gshare is the classic hash: index = PC XOR GHR, spreading (branch, history) pairs across the PHT:

Local history keeps a per-branch history register instead (captures patterns like taken-taken-not repeating); tournament predictors (Alpha 21264) run global and local side by side with a chooser table of 2-bit counters learning which to trust per branch.

TAGE uses tagged tables with geometrically increasing history lengths and a base predictor; the longest matching history usually supplies the prediction, with alternate-provider logic. Perceptrons use weighted history sums. Accuracy depends on workload, table capacity, and training.

Target Prediction

Branch target buffer (BTB): a small tagged cache, indexed by fetch PC, holding the predicted target and branch type. A BTB hit simultaneously answers “this is a branch” and “fetch from here next”, potentially redirecting fetch without a bubble, given a timely direction and target prediction:

Return address stack (RAS): returns can have different targets at the same return instruction, so a single BTB target is often insufficient. A small hardware stack (8-32 entries) pushes the address after a recognized call (PC+4, or PC+2 for a 16-bit call) and pops on every return; near-perfect until call depth overflows it. Speculative pushes/pops must be repaired on misprediction.

Indirect branches (virtual calls, switch tables, interpreter dispatch) have many targets per site; predicted with history-indexed target tables (ITTAGE), historically the worst-behaved class.

Stacking Predictors: A Real Frontend

A frontend can combine a small, fast next-PC predictor with a larger, slower direction predictor. The slower predictor may redirect fetch before execution detects an error. A fetch-target queue retains PCs and prediction metadata for training and recovery. Sizes and update policies are implementation-specific.

Living in the Pipeline

  • Predict in IF: BTB/direction lookup happens in parallel with the I-cache access, producing the next fetch PC.
  • Verify when the branch executes: compare actual outcome/target with prediction.
  • Recover on mismatch: squash all younger instructions, restore fetch to the correct path, and repair predictor state (GHR, RAS). In-order pipes flush stages; out-of-order machines restore a checkpoint, the same machinery as Exceptions recovery. A clean implementation tags every instruction with an epoch; instructions from stale epochs are discarded wherever they are.

How selective squash really works

BOOM refines the epoch idea into a branch mask: every in-flight instruction carries one bit per unresolved branch it depends on. When a branch resolves wrong, a single broadcast of its bit kills exactly the dependent instructions, wherever they sit, with no walking and no over-kill.

  • Update the tables at resolve/commit with the true outcome.

MPKI measures mispredictions per 1,000 instructions. Approximate added CPI is MPKI×penalty/1000MPKI\times penalty/1000. Wider machines can discard more work per misprediction; accuracy alone does not capture this cost.
