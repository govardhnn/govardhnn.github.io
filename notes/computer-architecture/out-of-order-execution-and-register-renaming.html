Out of Order Execution and Register Renaming

The in-order Simple Instruction Pipeline stalls whenever the next instruction is not ready, even if the ten after it are. A cache miss (hundreds of cycles, Caches and Virtual Memory) or a long FP operation (Floating Point Architecture) idles the whole machine. Out-of-order (OOO) execution lets ready instructions run around stalled ones: execute in dataflow order, but keep all effects in program order at commit.

True and False Dependencies

Hazard Pattern Nature
RAW (true) add x1,... then sub ...,x1 real dataflow; only faster execution helps
WAR (anti) sub ...,x1,... then add x1,... false: a name is reused
WAW (output) add x1,... then mul x1,... false: same

WAR/WAW exist only because the ISA has finitely many register names; the compiler must reuse them. The dataflow limit (execute every instruction as soon as its true operands are ready) is the theoretical speed of a program; eliminating false dependencies is how hardware approaches it.

Scoreboarding (CDC 6600, 1964) was the first OOO issue: a central table tracks which units and registers are busy, issuing instructions when safe, but it must stall on WAR/WAW because values live only in the architectural registers.

Register Renaming

Renaming removes false dependencies by giving every instruction’s destination a fresh physical register from a free list, and mapping architectural names through a rename map table. Physical registers outnumber architectural (e.g. 200+ vs 32) to name all in-flight values.

Program (arch regs) After rename Dependency removed
ld x1, 0(x2) ld p7, 0(p2)
add x3, x1, x4 add p8, p7, p4 RAW on x1 kept (p7)
sub x1, x5, x6 sub p9, p5, p6 WAW on x1 gone, runs immediately
or x7, x1, x3 or p10, p9, p8 reads the new x1 (p9), correct

The sub no longer waits for the load: same registers, no conflict. Map after: x1→p9, x3→p8, x7→p10. A physical register is freed when the next writer of the same architectural register commits (no one can still read the old value).

Tomasulo’s Algorithm

The IBM 360/91 FPU (1967) invented distributed renaming three years after the scoreboard:

  • Reservation stations (RS) in front of each functional unit hold waiting instructions. Each operand is either a value (already available, copied in) or a tag naming the RS that will produce it.
  • Register file entries carry a tag too: “the value is coming from RS kk”.
  • When a unit finishes, it broadcasts (tag, value) on the common data bus (CDB); every RS and register entry snoops it and captures a matching value. Dependents can issue the next cycle: forwarding falls out of the design.

Renaming lives in the tags (destinations are RS names, not register names), so WAR/WAW vanish. Modern machines keep the idea but shrink reservation stations to an issue queue holding only tags, since copying wide values into every RS wastes area and the CDB does not scale to many results per cycle. Rename Schemes in Real Machines

Three answers shipped, each defining where speculative and committed values sit:

ROB renaming Rename buffer Merged register file
speculative values in the ROB entry separate result buffer one physical register file
committed values architectural RF architectural RF the same physical file
allocation FIFO with the ROB, no free list FIFO, no free list explicit free list
at commit copy value ROB→ARF copy buffer→ARF update map; value never moves
used by Intel Core 2 (P6 line) IBM Power3 MIPS R10000, Alpha 21264, every modern core

The ROB scheme is the simplest (allocation is just the ROB’s own FIFO), and the rename buffer refines it with the observation that about a third of instructions produce no register result, so giving every ROB entry a value field wastes a third of the storage. But both write every result twice (buffer, then architectural file) and let an operand live in two places during its lifetime. The merged file pays for its free list and stale-mapping bookkeeping with values that are written once, never move, and always come from one place, the deciding advantages as width, ports, and energy budgets grew.

When is a physical register safe to free?

Not when its last reader commits: the hardware cannot know a reader is the last, because a mispredicted branch may be squashed and new readers of the old value fetched in its place. The safe rule: free p1 only when the next writer of the same architectural register commits; from that point no future instruction can be renamed to p1. This is why each instruction carries its stale mapping (what its destination register previously mapped to) through the ROB: that stale register is what commit frees.

BOOM (the Berkeley Out-of-Order Machine) is a documented merged-PRF core: 96 integer + 64 FP physical registers over 32+32 architectural in its base configuration. Each branch snapshots the map table for single-cycle misprediction recovery, and a per-branch allocation list records the registers allocated on the speculative path, so a squash returns them to the free list in one OR operation.

The Reorder Buffer and In-Order Commit

Pure Tomasulo updates registers as results appear, out of order, which wrecks precise exceptions and makes misspeculation unrecoverable. The fix separates execution order from commit order.

The reorder buffer (ROB) is a circular buffer allocated per instruction at dispatch, in program order:

  • Instructions execute whenever ready and mark their ROB entry done.
  • Commit happens only at the head, oldest first: the result becomes architectural, stores are released to memory, the entry is freed.
  • An exception or misprediction marked on an entry is acted on only when it reaches the head; everything younger is squashed and the rename map restored (from checkpoints taken at branches, or by walking the ROB). The speculative work simply never commits.

The modern OOO pipeline end to end:

fetch→decode→rename→dispatch (ROB + IQ)→issue/wakeup-select→execute→writeback→commit\text{fetch} \to \text{decode} \to \text{rename} \to \text{dispatch (ROB + IQ)} \to \text{issue/wakeup-select} \to \text{execute} \to \text{writeback} \to \text{commit}

The window (ROB size, 200-600+ entries in current cores) bounds how far ahead the machine can look for independent work; it is sized to keep executing across an L2-miss latency.

Memory Instructions

Registers rename cleanly; memory does not, because addresses are computed at runtime: does ld 0(x5) depend on the older sd 0(x3)? Unknown until both addresses resolve.

  • The store queue holds stores’ addresses and data until commit (memory must never see speculative stores). Loads search it: an address match means store-to-load forwarding (take the data directly); no match means go to cache.
  • The load queue remembers executed loads so a later-resolving older store can detect it forwarded nothing to a load that needed it: a memory-order violation, squash and replay the load.
  • Waiting for all older store addresses is slow, so cores use memory dependence prediction (e.g. store sets): predict which loads conflict, let the rest issue aggressively; mispredictions cost a replay.

BOOM makes the aggression concrete: loads fire to memory the moment their address resolves, CAM-searching the store queue on the way (forward if an older matching store has data; sleep and retry if it does not). The safety net sits at the other end of the pipe: every committing store CAM-searches the entire load queue, and a match means a load ran too early: flush the pipeline and reset the rename maps, “an incredibly expensive operation” in the project’s own documentation, tolerable only because it is rare.

Load reordering between cores is architecturally visible; what the ISA permits is the Memory Model.

Costs

OOO multiplies state (PRF, IQ, ROB, LSQ, checkpoints) and adds ~3 pipeline stages (rename, dispatch, issue), deepening the misprediction penalty that Branch Prediction must cover. The wakeup-select loop and load-store search are the scaling bottlenecks that shape Advanced Superscalar Architectures. The payoff: 2-4x IPC over in-order on pointer-chasing, cache-missing code, which is why every high-performance core since the mid-1990s pays it.
