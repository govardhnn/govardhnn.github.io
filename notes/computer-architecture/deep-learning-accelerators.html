Deep Learning Accelerators

Why Accelerators Now: The End of Free Scaling

Deep-learning accelerators are one instance of a broader shift. For decades, general-purpose CPUs got faster “for free” via two scaling laws - both of which have ended:

Scaling law Said Status
Moore’s Law Transistor count doubles ~every 2 years Slowing - and more transistors no longer help a serial program much
Dennard scaling Power density stays constant as transistors shrink (so you could clock faster each generation) Ended ~2005 - shrinking transistors no longer get proportionally lower power, giving the power wall and the multicore turn

With per-core frequency and the multicore dividend both tapped out (Amdahl limits how far more cores help - see the Performance section), the remaining lever for big efficiency gains is specialization: build hardware tailored to a specific domain. Hennessy & Patterson call this a “new golden age for computer architecture,” driven by domain-specific accelerators (DSAs).

Accelerator-Level Parallelism (ALP)

The systems framing: just as instruction-level, data-level, and thread-level parallelism were prior eras’ levers (see Parallel Programming), accelerator-level parallelism is the next - a system gets its work done by multiple specialized accelerators running concurrently, each far more efficient at its task than a general core.

Parallelism level Unit of concurrency
ILP Independent instructions (pipelining, superscalar, OoO)
DLP Independent data elements (SIMD, vector, GPU)
TLP Independent threads (multicore, SMT)
ALP Independent accelerators (NPU, GPU, ISP, video codec, DSP, modem…​ running at once)

[!note] ALP is already mainstream in smartphones - a modern SoC is mostly fixed-function/accelerator silicon (image signal processor, neural engine, video encode/decode, modem, GPU), with the CPU largely orchestrating them. The driver is energy: a dedicated accelerator can be 10-1000× more energy-efficient than a CPU for its task (the data-movement and overhead-elimination arguments later in this note), and energy is the binding constraint from phones to datacenters. The accelerators in this note (systolic/TPU-style DL engines) are the most prominent example, but the same logic produces the whole zoo of SoC accelerators.

Why Deep Learning Needs Custom Hardware

A deep neural network’s forward pass is overwhelmingly dominated by one operation: multiply-accumulate (MAC), applied billions of times per inference in dense matrix multiplications (fully-connected layers) and convolutions. General-purpose CPUs spend most of their transistor budget on control logic, branch prediction, and out-of-order scheduling (see the Microarchitecture section) - machinery that’s largely wasted on a workload that’s almost entirely regular, predictable MAC operations with very little control flow.

Platform Why it’s used / not used for DL
CPU General-purpose, flexible, but low arithmetic density per watt - most of the die isn’t doing MACs
GPU High arithmetic density via SIMT (see Parallel Programming section); the default training/inference platform today because of mature software ecosystems
FPGA Reconfigurable dataflow, lower power than GPU for some inference workloads, but harder to program and lower peak throughput
ASIC (TPU-style) Highest arithmetic density and energy efficiency for the operations it was built for - sacrifices flexibility entirely

This is the “virtuous cycle” framing from the deep learning hardware literature: better hardware enables bigger models and datasets, which produce better results, which justifies investment in even more specialized hardware - a self-reinforcing loop that’s been the core driver of accelerator design since the mid-2010s.

Dataflow Architectures and Systolic Arrays

A systolic array is a grid of simple processing elements (PEs), each doing one MAC per cycle, passing operands to neighboring PEs on every clock tick - data flows through the array like a pulse (hence “systolic”), with very little control overhead per PE.

// One PE in a systolic array: a single MAC, with operands flowing through
// to neighboring PEs each cycle - no instruction fetch/decode per PE at all.
module systolic_pe #(parameter W = 8, parameter ACC_W = 32) (
  input  logic                clk, reset,
  input  logic signed [W-1:0] a_in, b_in,      // from west/north neighbors
  output logic signed [W-1:0] a_out, b_out,    // to east/south neighbors
  output logic signed [ACC_W-1:0] acc
);
  always_ff @(posedge clk or posedge reset) begin
    if (reset) begin
      acc   <= '0;
      a_out <= '0;
      b_out <= '0;
    end else begin
      acc   <= acc + (a_in * b_in);   // accumulate the local MAC
      a_out <= a_in;                  // forward operands to the next PE
      b_out <= b_in;
    end
  end
endmodule

Connecting many of these PEs in a 2D grid lets an entire matrix multiplication stream through the array with data reused across many PEs as it flows - this is precisely the architecture behind Google’s TPU (Tensor Processing Unit) MXU (Matrix Multiply Unit).

Why a Bigger Fixed-Function Unit Wins: the Register-File Tax

Before systolic arrays, GPUs computed matrix multiplies the way an ordinary CPU core computes anything: a register file feeds a few arbitrary operands into an ALU, and the result writes back - one MAC at a time, with the ALU’s inputs selected from the register file by a multiplexer on every single operation.

That mux is not free. A mux selecting 1-of-n register-file entries, each p bits wide, built from the only two primitives available (AND, OR), costs:

n × p   AND gates  (mask every entry against its select line)
(n-1) × p   OR gates  (collapse the n masked entries down to 1)

A small, 8-entry, 32-bit register file already costs roughly 8 × 32 = 256 AND gates per read port - and a single MAC operation needs three read ports (two source operands, one accumulator) plus a write port. Compare that to the MAC’s own arithmetic: a p×q-bit multiply costs p×q AND gates plus p×q full adders (see the Multiplier section above) - for narrow, low-precision operands, the register file access can easily cost several times more gates than the actual computation it’s feeding.

[!note] This is the literal motivating argument for Tensor Cores / systolic arrays, not just a contributing factor: pre-Volta GPUs (and ordinary CPUs) were spending the overwhelming majority of their multiply-accumulate circuit area on register-file muxing, with only a small fraction actually doing arithmetic. A systolic array fixes this by amortizing one expensive register-file read across an entire 2D grid of PEs per trip through the register file, rather than paying the full mux cost for every single MAC - exactly the same “do more work per register-file access” principle the Dataflow Taxonomy below is built around.

Dataflow Taxonomy

A central design question for any DL accelerator: which operand stays fixed (stationary) in a PE across cycles, since that determines how much data movement (the dominant energy cost - see below) is needed.

Dataflow What stays stationary in each PE Data movement implication
Weight-stationary Weights loaded once, reused across many input activations Minimizes weight movement - good when weight reuse is high (e.g., large batch sizes)
Output-stationary Partial sums accumulate locally in each PE Minimizes movement of accumulator values - good when partial-sum traffic would otherwise dominate
Input/Row-stationary Input activations (or rows of them) stay local, reused across multiple filters Balances reuse of both weights and activations, at some added control complexity (the approach used by Eyeriss-style accelerators)

[!note] There is no universally best dataflow - the right choice depends on the layer’s shape (batch size, channel count, spatial dimensions). This is exactly why many real accelerator designs support more than one dataflow mode, or why compiler/mapper tools exist specifically to choose a dataflow per layer rather than fixing one choice for an entire network.

The Communication-Scaling Argument

A weight-stationary systolic array’s entire value proposition can be stated as one scaling relationship. For an x × y weight matrix held stationary in the array, multiplied repeatedly against streaming input vectors:

Compute done per trip through the register file  ~  x * y   (one MAC per array cell)
Data that must cross the register-file boundary  ~  x       (just the input/output vectors)

Compute scales with the area of the array (x × y), while the register-file traffic the design has to pay for only scales with one dimension (x) - because the weight matrix, once loaded, never needs to re-cross that boundary again for as long as it stays resident. This is exactly the same quadratic-vs-linear win the Multiplier section’s area analysis describes for arithmetic circuits, now applied one level up, to the cost of feeding data into the arithmetic rather than the arithmetic itself.

Loading the Stationary Operand

This leaves one question open: the weight matrix has to enter the array somehow before it can be reused for free. The standard answer is to pay that cost once, slowly, via a daisy-chained shift register running through the array:

// Conceptual weight-load shift chain: one weight value enters the top of
// each column per cycle, and every resident value shifts down by one row -
// after N cycles, an NxN array is fully loaded, using only N wires of
// bandwidth crossing the boundary (one per column), not N^2.
module systolic_weight_load #(parameter N = 4, parameter W = 8) (
  input  logic               clk,
  input  logic [W-1:0]       col_in [N],   // one new weight per column per cycle
  output logic [W-1:0]       grid   [N][N]
);
  always_ff @(posedge clk) begin
    for (int c = 0; c < N; c++) begin
      grid[0][c] <= col_in[c];                       // shift in at the top
      for (int r = 1; r < N; r++)
        grid[r][c] <= grid[r-1][c];                  // shift existing rows down
    end
  end
endmodule

Loading an N×N array this way takes N clock cycles and only N wires of register-file bandwidth - never N² - because only one new row enters per cycle while everything already resident shifts down by one position. Since weights are reloaded comparatively rarely (once per layer, or once per many thousands of input vectors), paying this slow, narrow load cost once is far cheaper than ever provisioning the wide, expensive wiring that loading the whole matrix in one shot would require.

Data Movement Dominates Energy

The single most important fact in DL accelerator design: moving a value is far more energy-expensive than computing with it.

Operation Relative energy cost (illustrative, classic accelerator energy breakdowns)
8-bit MAC (ALU operation itself) 1x (baseline)
Read from local register/PE buffer ~1x
Read from on-chip SRAM (scratchpad/cache) ~6x
Read from off-chip DRAM ~200x

This ordering - compute is cheap, off-chip memory access is catastrophically expensive - is the entire justification for systolic arrays’ local operand-forwarding, for large on-chip scratchpad buffers sized to avoid DRAM round-trips, and for every dataflow choice above: every one of them is fundamentally an exercise in minimizing the amount and distance of data movement, not minimizing arithmetic operation count (which is already cheap by comparison).

Quantization

Most DL accelerators compute in reduced precision (8-bit integer, or narrower) rather than the 32-bit floating point used during model training, since inference accuracy tolerates far more numerical error than the training process does.

Format Used for Tradeoff
FP32 Training (need precise gradients) Highest accuracy, lowest arithmetic density
FP16/BF16 Training (mixed precision) / inference Halves memory traffic and roughly doubles arithmetic density vs. FP32, with small accuracy loss given proper scaling
INT8 Inference ~4x the arithmetic density of FP32 hardware in the same area; requires careful calibration (scale/zero-point selection) to avoid accuracy loss
INT4 / binary / ternary Aggressive, often research/edge-specific inference Maximum density, but a real accuracy cost that must be validated per-model

Quantization is a direct lever on both halves of the data movement problem above: an 8-bit value is a quarter the size of a 32-bit float, which quarters its DRAM/SRAM bandwidth cost and lets a fixed-size MAC array hold four times as many narrow MAC units in the same area.

Why Halving Precision Buys More Than 2x

Recall from the Multiplier section in the Building Blocks section that a p×q-bit multiplier costs p×q full adders - area scales with the product of the operand widths, not their sum. Halving both operand widths (e.g., FP8 → FP4) therefore shrinks multiplier area by (1/2)×(1/2) = 1/4, not 1/2 - meaning a fixed silicon budget should fit four times as many multipliers, not two, when precision is halved.

[!note] This is a real, checkable discrepancy in publicly reported accelerator specs: prior to NVIDIA’s B100/B200 generation, halving precision was advertised as exactly doubling FLOP throughput - consistent with a linear area model, not the quadratic one above. Starting with B300, NVIDIA’s own specifications list FP4 throughput at roughly 3x FP8, not 4x - closer to (but still short of) what the quadratic scaling argument predicts, with the shortfall attributable to non-multiplier overhead (accumulator width, control logic, data movement) that doesn’t shrink as fast as the multiplier array itself.

This quadratic relationship is the single biggest reason low-precision arithmetic has paid off so well for neural network inference: every precision reduction is rewarded more than proportionally in the multiplier array, on top of (not instead of) the linear data-movement savings described above.

Sparsity

Many trained networks have a large fraction of near-zero weights (weight sparsity) and/or produce many zero activations at runtime (e.g., after a ReLU - activation sparsity). A MAC against a known-zero operand contributes nothing to the result, so skipping it saves both energy and time, if the hardware can detect and exploit it.

Sparsity exploitation Mechanism
Zero-skipping Detect a zero operand and skip issuing that MAC entirely, advancing to the next nonzero element
Compressed encoding Store only nonzero weights/activations plus their indices (e.g., compressed sparse row-style formats), reducing both storage and the corresponding memory traffic
Structured pruning Force sparsity into a hardware-friendly pattern (e.g., entire channels or fixed-size blocks pruned together) so the skipping logic stays simple and regular, at some cost in achievable sparsity ratio vs. unstructured pruning

[!warning] Unstructured sparsity (zeros scattered arbitrarily) is easy to achieve in software but hard to exploit efficiently in hardware - the irregular pattern of nonzero elements defeats the regular, pipelined dataflow that gives systolic arrays their efficiency in the first place. This tension between achievable sparsity ratio and hardware-exploitable sparsity structure is a recurring theme across accelerator designs.

Scratchpad Memory vs. Cache

CPUs (and GPUs) hide DRAM latency with a cache: the hardware transparently decides what stays on-chip, based on recent access history, and software simply issues ordinary loads/stores without knowing whether a given access will hit or miss. DL accelerators (TPUs in particular) instead expose a scratchpad: software explicitly issues a different instruction to move data between off-chip HBM/DRAM and the on-chip buffer, and a separate instruction to operate on data already resident there.

Cache (CPU/GPU) Scratchpad (TPU-style)
Who decides what’s on-chip Hardware, dynamically, based on access history Software/compiler, statically, ahead of time
Latency Non-deterministic - depends on hit/miss, which depends on what else has run recently Deterministic - an access to the scratchpad always takes the same number of cycles
Programming model Transparent - ordinary loads/stores, no separate addressing Explicit - distinct instructions/address space for scratchpad vs. off-chip memory
Where else this tradeoff appears Same hit/miss-driven design as the multicore cache hierarchies in the Multicore Cache Hierarchy Design section Same explicit-management philosophy as the FPGA/ASIC dataflow design choices above

This determinism is exactly what lets a DL compiler statically schedule an entire matrix multiply’s data movement in advance - when every access latency is known ahead of time, the scheduler can pack the systolic array’s input/output pipeline as tightly as the hardware allows, something it fundamentally cannot do if any given access might silently cost 100x more on a cache miss. The cost of that determinism is flexibility: software, not hardware, now has to get the scratchpad management right, since there’s no automatic fallback the way a cache miss provides.

GPU vs. TPU Floorplan

Beyond the per-core dataflow choices above, GPUs and TPUs differ in how many compute units they tile across the chip and how coarse-grained each one is - a choice with direct consequences for how much wiring bandwidth is available between compute and memory.

GPU TPU
Top-level structure Many small, nearly-identical units (Streaming Multiprocessors), each with its own small register file, warp scheduler, and small tensor core A few large, coarse-grained matrix units (MXUs) sharing one or a few vector units
Granularity analogy Each SM is, structurally, a small TPU - a small systolic array plus local control The whole chip is like one SM scaled up enormously
Data movement between vector and matrix units High - many parallel SMs, each with short, local, abundant wiring between its own vector/tensor units Lower - data has to cross through a comparatively narrow perimeter boundary into/out of each large MXU, rather than many short internal paths

[!note] This is the same register-file-tax tradeoff from earlier in this note, playing out at a different granularity. Many small units (GPU) keep wiring local and abundant but pay the register-file/control overhead per unit, many times over. Few large units (TPU) amortize that overhead across a much bigger systolic array, but pay for it with comparatively constrained perimeter bandwidth between the vector unit and the matrix unit - exactly mirroring the area-vs-communication tradeoff the Dataflow Architectures section above derives for the systolic array’s internal register-file access, now happening one level up, between major chip blocks instead of between PEs.

This tradeoff is precisely why GPUs remain the more flexible, general target for irregular or smaller workloads (more, smaller systolic arrays mean better load-balancing across heterogeneous work), while TPU-style chips win specifically on very large, very regular matrix multiplications, where the lower per-unit overhead and larger systolic array more than compensate for the narrower perimeter bandwidth into each unit.

Safe vs. Unsafe Optimizations

A useful framing (from accelerator design-space exploration methodology): some optimizations preserve a model’s output exactly, others trade some accuracy for efficiency, and the two need very different validation effort.

Category Examples Validation needed
Safe Architectural parallelism, pipelining, on-chip buffer sizing Standard hardware verification - output is bit-exact regardless
Unsafe Quantization, pruning/sparsity, voltage overscaling, SRAM fault tolerance (running memory below its rated reliability margin for power savings) Must be validated against model accuracy on real data, not just functional correctness - a “passing” chip can still silently produce a worse model

This distinction matters because it changes what you have to test: “safe” optimizations are verified the same way any other digital design is (the synthesis/timing-analysis methodology in the Synthesis and Timing Analysis section applies unchanged); “unsafe” optimizations additionally require re-validating end-to-end model accuracy, since a perfectly functioning chip can still degrade the network’s actual predictions if pushed too aggressively on quantization, pruning, or fault tolerance.
