DRAM and Main Memory

Where Main Memory Sits

The cache hierarchy notes (Multicore Cache Hierarchy Design, Virtual Memory) treat “main memory” as the slow tier a cache miss falls through to. This note opens that black box: main memory is almost universally DRAM (Dynamic Random Access Memory), and its internal organization, timing, and scheduling have first-order effects on system performance - the memory wall (memory speed improving far slower than compute) is the single dominant scaling problem in modern systems.

Property SRAM (caches) DRAM (main memory)
Cell 6 transistors, bistable latch 1 transistor + 1 capacitor - the charge on the capacitor is the bit
Density Low (6T per bit) High (1T1C per bit) - why main memory is DRAM, not SRAM
Speed Fast (sub-ns) Slow (tens of ns) - the capacitor must be sensed by tiny analog signals
Volatility Holds value while powered Charge leaks - must be periodically refreshed or data is lost (the “Dynamic” in DRAM)

The 1T1C cell is the entire story behind DRAM’s character: it’s dense and cheap (one tiny capacitor per bit), but reading it is a slow, destructive, analog operation, and the stored charge decays on its own - every awkward property below traces back to “the bit is just charge on a leaky capacitor.”

DRAM Organization

DRAM is hierarchical, and every level exists to expose parallelism or amortize cost:

Level What it is
Channel An independent memory bus between the controller and a set of DRAM chips - different channels operate fully in parallel
Rank A set of DRAM chips operated together (ganged) to supply one full cache-line-wide data word per access
Bank An independent 2D array within a rank that can process a request in parallel with other banks - bank-level parallelism is the primary way DRAM hides its own latency
Row (page) One horizontal line of cells in a bank’s array - typically a few KB; the unit that gets read into the row buffer at once
Column The cache-line-sized slice within an activated row that an individual read/write actually transfers

A Bank and its Row Buffer

Inside one bank, a 2D array of 1T1C cells is addressed by a row decoder and a column mux. Crucially, you cannot read a single cell directly - the capacitor’s charge is far too small to drive an output. Instead:

ACTIVATE (row address):  the entire row's cells dump their charge onto the
                         bitlines; sense amplifiers detect and latch the
                         whole row into the ROW BUFFER (a row of sense amps)

READ/WRITE (column addr): transfer one cache-line-sized column out of the
                         row buffer - fast, because it's now just reading
                         latched values, not sensing leaky capacitors

PRECHARGE:               close the row - reset the bitlines so a different
                         row can be activated next

[!warning] ACTIVATE is destructive - dumping the cells’ charge onto the bitlines empties the capacitors. The sense amplifiers therefore also write the row back as part of activation, restoring the charge they just drained. This is why a DRAM read is fundamentally a read-modify-restore cycle, not a simple lookup, and it’s the same mechanism that makes refresh (below) possible.

Row Buffer Locality

Because the row buffer holds a whole row (page), the latency of an access depends entirely on what’s currently sitting in that bank’s row buffer:

Case What happens Relative latency
Row hit Requested row is already in the row buffer Fast - just a column read, no ACTIVATE needed
Row miss (empty) Row buffer is closed/empty Medium - ACTIVATE then read
Row conflict A different row is open in the buffer Slow - PRECHARGE the old row, then ACTIVATE the new one, then read

This is exactly analogous to a cache hit/miss, one level down - and it’s why DRAM access latency is not a single fixed number. The same address stream can see wildly different effective latency depending on how well consecutive accesses hit the same rows (row-buffer locality can range from ~96% hit rate for streaming access to ~3% for random access).

Open-Row vs. Closed-Row Policy

After an access completes, the controller must decide whether to leave the row open:

Policy After an access Bets that the next access…​
Open-row Leave the row in the buffer …​is to the same row (row hit) - pays a row-conflict penalty if wrong
Closed-row PRECHARGE immediately …​is to a different row - avoids conflict, but pays an ACTIVATE even if the next access was to the same row
Adaptive Predict per-bank based on recent access pattern …​behaves like whichever of the above the predictor expects

The right choice depends on workload locality, which is precisely why real controllers use adaptive policies - the same open-vs-closed tension as the branch-prediction and cache-replacement bets covered in other notes: speculate on locality, pay a penalty when the speculation is wrong.

The Memory Controller

The memory controller is a dedicated on-chip engine that translates the stream of cache-miss requests into the low-level DRAM command sequence (ACTIVATE / READ / WRITE / PRECHARGE / REFRESH), subject to dozens of timing constraints, while trying to maximize throughput and fairness. It’s one of the most performance-critical and least-software-visible blocks in the entire machine.

DRAM Scheduling: FR-FCFS

The controller has a request buffer of pending accesses and chooses which to issue next - a scheduling problem directly analogous to instruction scheduling in an out-of-order core (see the Microarchitecture section), but optimizing for row-buffer locality instead of operand readiness.

Policy Priority order
FCFS Oldest request first - simple, but ignores row-buffer state, so it suffers constant row conflicts
FR-FCFS (1) Row-hit requests first, then (2) oldest first - the standard baseline 
FR-FCFS prioritization (applied at the DRAM *command* level):
  1. Ready column commands (read/write to an already-open row) - row hits
  2. Among those, the oldest request
  3. Only then issue row commands (activate/precharge) to open new rows

FR-FCFS maximizes DRAM throughput by draining all the row hits to an open row before paying to switch rows - but this same greediness is a fairness hazard in a multicore system: a thread with high row-buffer locality (streaming) can starve a thread with low locality (random access), because the streaming thread’s requests keep jumping the queue as row hits. This is the memory-system analogue of the cache-partitioning/QoS problem in the Multicore Cache Hierarchy Design section, and it’s why fairness-aware memory schedulers are an active research area.

Address Mapping

The controller also decides how a physical address’s bits map onto channel / rank / bank / row / column. This choice is not neutral - it directly determines how much parallelism a given access stream can extract:

Mapping choice Effect
Consecutive addresses → same row, different columns Maximizes row-buffer hits for streaming access (sequential data stays in one open row)
Consecutive addresses → different banks/channels Maximizes bank/channel-level parallelism (spreads a burst across independent units)

These two goals are in tension - packing sequential accesses into one row for locality is the opposite of spreading them across banks for parallelism. Real mappings (e.g., XOR-based bank hashing) try to balance the two and avoid pathological cases where a strided access pattern repeatedly hits the same bank and serializes (a bank conflict).

Refresh

Because the 1T1C capacitor leaks, every cell must be read-and-restored periodically or it loses its value. The DRAM standard guarantees data retention only if every row is refreshed within a retention time window (traditionally 64 ms).

Cost of refresh Detail
Performance While a bank is being refreshed, it cannot serve requests - refresh steals memory bandwidth and adds latency
Energy Refresh is a constant background power draw, significant in large-capacity and mobile systems
Scaling Refresh overhead grows with capacity - more rows to refresh in the same window - making it a worsening problem as DRAM density increases

[!note] A key Mutlu-group observation: the 64 ms retention requirement is set by the worst-case leakiest cell in the entire chip, but the vast majority of cells could safely go far longer without refresh. This motivates retention-aware refresh schemes that refresh weak rows often and strong rows rarely - turning a uniform worst-case tax into a per-row-tailored one. It also connects directly to the reliability problems in the Memory Robustness and RowHammer section: refresh, retention, and reliability are all facets of “the bit is just decaying charge on a capacitor.”

The Memory Wall

The framing that motivates this entire note: processor performance historically improved much faster than DRAM latency, so over decades the relative cost of a memory access (measured in wasted processor cycles) has grown enormously. A modern cache miss to DRAM can cost hundreds of core cycles - which is why nearly every technique in the surrounding notes (deep cache hierarchies, prefetching, out-of-order execution to overlap misses, and multithreading to hide stalls) exists fundamentally to tolerate or avoid main-memory latency rather than reduce it. DRAM latency itself has improved only modestly across many generations, even as bandwidth and capacity have scaled - making latency, not bandwidth or capacity, the hardest and most persistent of the three to fix.

Memory Robustness and RowHammer

The Core Problem: DRAM Is Analog Underneath

The DRAM and Main Memory section established that a DRAM bit is just charge on a leaky 1T1C capacitor, sensed by tiny analog signals. As process technology shrinks cells closer together, that analog substrate stops behaving like the clean digital abstraction the rest of the stack assumes. Memory robustness is the study of how, and how often, DRAM silently returns the wrong bit - and what to do about it.

Two distinct failure modes dominate, both tracing to the same root cause (“a bit is decaying, weakly-isolated charge”):

Failure mode Cause
Retention errors A cell leaks its charge away before the next refresh - data simply fades
Disturbance errors (RowHammer) Accessing one cell drains charge from a neighboring cell through electrical coupling - data is corrupted by activity elsewhere

Retention Errors

Refresh (covered in the DRAM section) exists precisely to prevent retention errors - every row must be refreshed within the retention-time window (traditionally 64 ms) or its weakest cells lose their value.

The subtlety is that retention time is not uniform:

Property Consequence
Per-cell variation A few “weak” cells leak far faster than the average; the 64 ms standard is set by the worst case across the whole chip
Data-pattern dependence A cell’s retention time depends on the values stored in neighboring cells (coupling again) - so the same cell can pass at one data pattern and fail at another
Temperature dependence Leakage roughly doubles every ~10 °C - hotter chips need more frequent refresh
Variable retention time (VRT) Some cells randomly switch between long and short retention states over time - defeating any one-time profiling of weak cells

[!warning] VRT is what makes retention errors genuinely hard: you cannot simply test a chip once, find the weak cells, and refresh only those forever - a cell that profiled as “strong” can spontaneously become “weak” later. This is why retention-aware refresh schemes have to be conservative or combine profiling with error-correcting codes, and why retention remains an open reliability problem rather than a solved one.

RowHammer

The headline DRAM reliability/security problem, and a signature result of Mutlu’s group (Kim et al., ISCA 2014, “Flipping Bits in Memory Without Accessing Them”).

The Mechanism

Repeatedly activating and precharging one DRAM row (the aggressor) many times before the next refresh induces bit flips in physically adjacent rows (the victims) - even though the victim rows were never accessed at all.

Repeat many times within one refresh window:
  ACTIVATE aggressor row    <- toggling the aggressor's wordline high...
  PRECHARGE aggressor row   <- ...then low, again and again

Result: cells in the PHYSICALLY ADJACENT victim rows lose enough charge
        to flip - without those rows ever being read or written

The cause is the same cell-to-cell coupling behind data-pattern-dependent retention: activating a row raises its wordline voltage, which slightly disturbs adjacent rows through electrical interference. Each activation drains a tiny bit of charge from neighbors; hammer enough times before refresh restores them, and a vulnerable victim cell flips.

[!note] RowHammer is not a rare manufacturing defect - the original study found the large majority of commodity DRAM modules from major vendors (2012-2013 onward) were vulnerable, and newer, denser DRAM is more vulnerable, not less, because shrinking cells closer together strengthens exactly the coupling that causes it. This is the central worry: the trend that makes DRAM cheaper and denser (the entire economic driver of the memory industry) is the same trend that makes RowHammer worse.

Why It’s a Security Vulnerability, Not Just a Reliability Bug

A bit flip an attacker can induce on demand in memory they don’t own is a security primitive. The attacker hammers rows they are allowed to access, to flip bits in an adjacent victim row they are not - and if the victim row happens to hold security-critical state, that’s a privilege escalation:

Exploit class What gets flipped
Page-table corruption Flip a bit in a page-table entry to gain write access to a page the attacker shouldn’t own - kernel privilege escalation from userspace
Sandbox escape Flip bits to corrupt a managed-runtime / browser sandbox’s safety checks
Remote attacks Demonstrated even from JavaScript in a browser, and across VMs in a cloud host (one tenant flipping another’s memory)

This is the higher-level implication Mutlu emphasizes: a circuit-level failure mechanism (charge coupling between adjacent cells) punches straight through every layer of the abstraction hierarchy - architecture, OS, sandbox, language - to become an exploitable, sometimes remote, security hole. It’s a concrete refutation of the assumption that the digital abstraction can be reasoned about without regard to the analog reality underneath.

Mitigations

Mitigation Approach Limitation
Increased refresh Refresh more often, shrinking the hammering window Costly (bandwidth/energy, per the DRAM section); doesn’t fully close the window as vulnerability worsens
Target Row Refresh (TRR) Hardware tracks frequently-activated rows and refreshes their neighbors early Many deployed TRR implementations were later broken by more sophisticated access patterns (see below)
ECC (error-correcting codes) Detect/correct flipped bits with redundancy Corrects only a few bits per word; multi-bit RowHammer flips can exceed its correction capacity, and ECC was not designed as a security mechanism
PRAC (Per Row Activation Counting) Newer standard: count activations per row in hardware, trigger a mitigating refresh past a threshold More principled, but adds cost and is still being hardened against worst-case patterns

[!warning] RowHammer mitigation has been a years-long cat-and-mouse cycle. Each deployed defense (single-sided assumptions, then TRR) was subsequently defeated by more advanced access patterns - double-sided hammering (hammering both rows adjacent to a victim), many-sided hammering (to overwhelm the limited tracking tables of TRR), and half-double (exploiting interactions between a defense’s own mitigating refreshes). The lesson Mutlu draws is that RowHammer cannot be reliably patched as an afterthought - robust defense has to be designed into the DRAM and controller from the start, with provable guarantees rather than heuristic tracking.

The Broader Point: Robustness as a First-Class Constraint

The unifying theme across retention and RowHammer is that scaling - the relentless shrinking of DRAM cells that delivers density and cost improvements - directly erodes the digital abstraction by strengthening leakage and cell-to-cell coupling. This reframes memory design: reliability and security are not features bolted onto a working memory, they are fundamental constraints that scale against you, and they connect to the same physical reality (decaying, weakly-isolated charge) that the DRAM section’s refresh discussion and the Flash and SSDs section’s wear/disturb discussion both grapple with at different points in the memory hierarchy.

Flash Memory and SSDs

Where Flash Sits

Below DRAM in the memory hierarchy sits non-volatile storage. Modern storage is increasingly NAND flash (SSDs) rather than spinning disk. Flash is its own kind of analog-underneath device - like DRAM (see the DRAM and Main Memory and Memory Robustness notes), its quirks all trace to the physics of how it stores a bit, and those quirks shape an entire software layer (the FTL) that exists to hide them.

Tier Technology Volatile? Defining quirk
Caches SRAM Yes Fast but low density
Main memory DRAM Yes Leaky charge → needs refresh
Storage NAND flash No Charge on a floating gate; erase-before-write + limited write endurance

The Flash Cell

A flash cell stores a bit (or several) as charge trapped on a floating gate - electrically isolated, so the charge stays without power (hence non-volatile). The amount of trapped charge shifts the transistor’s threshold voltage, which is what a read senses.

How many bits one cell holds is a direct density-vs-reliability trade, because it amounts to slicing the analog charge level into more distinguishable bands:

Type Bits/cell Voltage levels Tradeoff
SLC 1 2 Fastest, most durable, most expensive per bit
MLC 2 4 2x density, slower, less durable
TLC 3 8 More density still, slower reads/writes, lower endurance
QLC 4 16 Highest density, slowest, lowest endurance - bands so close that distinguishing them is delicate

The progression SLC → QLC is the same density-vs-margin tradeoff as quantization in the Deep Learning Accelerators section, in hardware: packing more levels into the same physical analog range (more bits per cell) buys density but shrinks the noise margin between levels, costing speed and reliability.

The Defining Constraint: Erase-Before-Write

The single property that shapes everything about SSD design: flash has an asymmetry between the granularity of its three operations.

Operation Granularity Notes
Read Page (e.g., 4-16 KB) Fast
Program (write) Page Can only write a page that is currently erased - can’t overwrite in place
Erase Block (many pages, e.g., hundreds) Slow, and the only way to reset pages back to writable - far coarser than read/write

[!warning] You cannot overwrite a flash page in place. To change data already written, the controller must write the new version to a different, already-erased page and mark the old one invalid - because erasing happens only at the much coarser block granularity, and you can’t erase one page without erasing its hundreds of neighbors. This single mismatch (write at page granularity, erase at block granularity) is the root cause of every piece of SSD complexity below.

The Flash Translation Layer (FTL)

The FTL is the firmware (running on the SSD’s own controller, with its own DRAM) that hides flash’s quirks behind the simple “read/write a logical block” interface the host OS expects. It is, in effect, an entire little operating system for the flash.

Logical-to-Physical Mapping

The FTL maintains a map from logical page addresses (what the host uses) to physical page addresses (where the data actually lives). This indirection is what makes erase-before-write invisible: an overwrite of logical page L just redirects `L’s mapping to a fresh physical page, leaving the old physical page to be reclaimed later.

Host writes logical page L (again):
  1. FTL picks a fresh, already-erased physical page P_new
  2. Writes the new data to P_new
  3. Updates mapping:  L -> P_new   (was L -> P_old)
  4. Marks P_old as INVALID (stale, awaiting reclaim)

Garbage Collection

Invalid pages accumulate and must eventually be reclaimed - but reclaiming requires erasing, which works only at block granularity, and a block to be erased usually still contains some valid pages mixed in with the invalid ones:

Garbage collection (to free up space):
  1. Pick a victim block (ideally one with mostly-invalid pages)
  2. Copy its still-VALID pages elsewhere (to a fresh block)
  3. Erase the victim block -> now fully reusable

[!note] This copying is write amplification - one logical host write can trigger several physical flash writes (the original, plus valid pages shuffled during GC). Write amplification directly consumes endurance and bandwidth, which is why SSD performance is workload-dependent and can degrade as the drive fills (less free space → GC must reclaim fuller blocks → more valid-page copying per erase).

Wear Leveling

Each flash block survives only a limited number of program/erase (P/E) cycles before it wears out - the floating gate’s insulation degrades with each erase, eventually trapping charge unreliably. Endurance ranges from ~100k P/E cycles (SLC) down to ~1k or less (QLC).

If some blocks were erased far more than others, those hot blocks would die while the rest of the drive was still healthy. Wear leveling spreads P/E cycles evenly across all blocks (e.g., by swapping hot and cold data) so the whole drive wears out together rather than failing in patches - the FTL tracks a per-block P/E count as metadata specifically to drive this.

Reliability: Read Disturb and Retention

Like DRAM, flash has analog disturbance and retention failure modes - the same family of problems as the Memory Robustness section, in a different cell technology:

Failure mode Cause Mitigation
Read disturb Reading a page slightly disturbs the charge on other pages in the same block (the flash analogue of DRAM RowHammer) Track read counts; refresh (rewrite) a block that’s been read too many times
Retention errors Trapped charge slowly leaks over months/years, especially in worn or hot cells Stronger ECC; periodic data refresh of old data
Program/erase wear Repeated erasing degrades the insulation, raising error rates over the drive’s life ECC strength scaled to wear; wear leveling to delay onset

Every modern SSD therefore runs strong error-correcting codes (far stronger than DRAM ECC) on every read as a matter of course - flash is expected to return raw bit errors, and the ECC is what turns the noisy analog device into the reliable digital block-storage abstraction the OS sees. This is the same theme as the rest of the memory hierarchy: the clean digital interface is a fiction maintained, at real cost, on top of an analog substrate that’s getting noisier as it scales denser (SLC → QLC).
